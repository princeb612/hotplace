# IO-003 — ASN.1 testcase reinforcement candidates

- **Area:** `test/testcase/asn.1`
- **Status:** Open
- **Kind:** Focused testcase improvement
- **Source basis:** Candidate list in the source-tree testcase README during the Revision 1107 review. These are proposals, not tests already added.

## Background

The ASN.1 testcase README contains a “Practical testcase reinforcement candidates” section. It calls out gaps where current test flow may exercise parsing or reconstruction without asserting a sufficiently strong end-to-end property.

The visible first candidates include:

1. Turn the YAML DER vector path into a round-trip check by comparing republished DER with the input when canonical byte identity is expected; if BER/non-canonical input is intentionally allowed, compare against an explicit canonical DER expectation instead.
2. Assert intermediate parser/reconstruction statuses in notation reconstruction rather than relying only on the final output.

3. Add a second decode only where it adds value. For selected deterministic DER cases, feed re-encoded bytes into a fresh module/value path and assert decode success, complete consumption, and expected notation/value. This establishes encode → decode → re-encode → re-decode only for those selected cases; it should not be implied for the suite as a whole.

Priority is 1 and 2: they strengthen existing paths with small, local assertions. Candidate 3 is a deliberate extension, not a requirement to duplicate every vector across the entire suite.

## Current understanding

- The list is about a few high-value assertions, not broad coverage percentages or a QA expansion.
- Raw byte equality is appropriate only where DER canonicality is the intended property.
- A logged or generated output is not equivalent to an assertion about expected semantic or wire-level output.
