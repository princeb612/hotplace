## RFC 6347 summary

Here is a visual summary and structured overview of the major components, message flows, and key specifications of the DTLS 1.2 protocol based on RFC 6347.

### 1. High-Level Architecture & Protocol Layering

DTLS 1.2 adapts TLS 1.2 for datagram transport (e.g., UDP) by preserving datagram semantics while adding packet loss handling, reordering protection, and denial-of-service (DoS) countermeasures.

```
+-----------------------------------------------------------------------+
|                      DTLS Handshaking Protocols                       |
|  +------------------+  +---------------+  +------------+  +--------+  |
|  |    Handshake     |  | Change Cipher |  |   Alert    |  | App    |  |
|  |     Protocol     |  | Spec Protocol |  |  Protocol  |  | Data   |  |
|  +------------------+  +---------------+  +------------+  +--------+  |
+-----------------------------------------------------------------------+
|                          DTLS Record Protocol                         |
|    (Explicit Epoch/Sequence # -> Fragmentation -> MAC/AEAD -> Encr)   |
+-----------------------------------------------------------------------+
|               Transport Layer (UDP, DCCP, SCTP, etc.)                 |
+-----------------------------------------------------------------------+
```

### 2. Handshake Message Flows

A. Full Handshake Flow (with Stateless Cookie Exchange)
To protect servers against DoS/amplification attacks, DTLS introduces a stateless cookie exchange before allocating handshake resources.

```
  Client                                               Server

ClientHello (no cookie)      -------->
                             <-------- HelloVerifyRequest (cookie)    [Flight 2]
ClientHello (with cookie)    -------->                                [Flight 3]
                                                ServerHello \
                                               Certificate*  \
                                         ServerKeyExchange*   Flight 4
                                        CertificateRequest*  /
                             <--------      ServerHelloDone /
Certificate*                 \
ClientKeyExchange             \
CertificateVerify*             Flight 5
[ChangeCipherSpec]            /
Finished                     -------->
                                         [ChangeCipherSpec] \ Flight 6
                             <--------             Finished /
Application Data             <------->     Application Data

(* Indicates optional or situation-dependent messages)
```

B. Session-Resuming Handshake Flow (No Cookie Exchange)
Session resumption skips the stateless cookie exchange when configured.

```
  Client                                               Server

ClientHello                  -------->                                [Flight 1]
                                                ServerHello \
                                         [ChangeCipherSpec]  Flight 2
                             <--------             Finished /
[ChangeCipherSpec]           \ Flight 3
Finished                     -------->
Application Data             <------->     Application Data
```

### 4. Summary of Key Concepts & Differences from TLS 1.2

Core Mechanisms for Unreliable Transport
- Explicit Sequence Numbers & Epochs: The record layer includes explicit epoch (incremented on cipher state changes) and sequence_number (48-bit) fields to handle packet reordering and enable independent MAC verification.
- Stateless Cookie Exchange: HelloVerifyRequest forces clients to demonstrate IP reachability before the server allocates resources.
- Handshake Fragmentation & Reassembly: Explicit message_seq, fragment_offset, and fragment_length fields in the handshake header allow large handshake messages to span multiple datagrams.
- Timer & Retransmission State Machine: Handshake messages are grouped into flights. Monolithic retransmission timers (starting at 1s and doubling up to 60s) handle lost flights.
- Replay Detection: Employs a sliding window algorithm (minimum 32-bit, default 64-bit window) similar to IPsec ESP to discard duplicate records.

Primary Operational Differences
- Stream Cipher Ban: Stream ciphers (such as RC4) are prohibited because they require strictly ordered, continuous decryption streams.
- Invalid Record Handling: Invalid MACs or malformed records SHOULD be silently discarded to maintain connection stability, rather than terminating the connection immediately as in TLS.
- PMTU Sizing: Each DTLS record MUST fit inside a single datagram to avoid IP layer fragmentation. Handshake layers dynamically adapt fragment sizes to PMTU constraints.
