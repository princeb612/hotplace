## RFC 9001

### QUIC Security Architecture (RFC 9001 Overview)
RFC 9001 defines how Transport Layer Security (TLS 1.3) integrates with QUIC to provide confidentiality, integrity, and peer authentication. Unlike standard TLS over TCP, QUIC eliminates the TLS Record Layer; QUIC directly encapsulates TLS handshake messages into its own CRYPTO frames while relying on TLS for key generation and parameter negotiation.

### Core Security Mechanisms
- TLS 1.3 Integration: QUIC uses TLS 1.3 exclusively to conduct authenticated key exchanges. Standard TLS record protection is omitted; QUIC handles framing, sequencing, and packet encryption.
- Encryption Levels & Keys: Communication transitions through four distinct encryption levels—Initial, 0-RTT, Handshake, and 1-RTT—each tied to independent packet number spaces and key sets.
- Header Protection: AEAD encrypts packet payloads, while a separate mechanism hides sensitive packet header fields (such as packet numbers and key phase bits) using AES-ECB or ChaCha20 masks.
- Key Update: Once the handshake is confirmed, endpoints can independently trigger key updates by toggling the Key Phase bit without using TLS KeyUpdate control messages.
- Replay Protection & Limits: 0-RTT application data is susceptible to replay attacks; applications must enforce idempotency or strict 0-RTT profiles. AEAD algorithms carry strict confidentiality and integrity packet limits (e.g., $2^{23}$ encrypted packets for AES-GCM).

### Technical Specifications Summary
| Feature / Aspect | Specification / Protocol Rule |
| -- | -- |
| Minimum TLS Version | TLS 1.3 (Older TLS versions strictly prohibited) |
| Header Protection Algorithms | AES-ECB (for AES-GCM/CCM) or Raw ChaCha20 |
| AES-GCM Packet Limits | Confidentiality: $2^{23}$ packets; Integrity: $2^{52}$ failed packets |
| Alert Handling | TLS Alerts mapped to QUIC error codes ($0\text{x}0100 + \text{AlertDescription}$) |
| Disallowed Features | Post-handshake Auth, TLS Middlebox Compatibility, EndOfEarlyData |
