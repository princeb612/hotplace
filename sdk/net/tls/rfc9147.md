## RFC 9147 summary

This document (RFC 9147) specifies Datagram Transport Layer Security (DTLS) Protocol Version 1.3. It updates and obsoletes DTLS 1.2 (RFC 6347) while aligning closely with TLS 1.3 (RFC 8446) to provide equivalent security guarantees for datagram transports like UDP.

### 1. Protocol Flow Diagram (Full Handshake with Cookie Exchange)

```
Client                                                  Server
------                                                  ------
ClientHello (epoch=0)       -------->
                            <--------        HelloRetryRequest + cookie (epoch=0)
ClientHello + cookie        -------->
(epoch=0)
                                                    ServerHello (epoch=0)
                                                    {EncryptedExtensions} (epoch=2)
                                                    {Certificate*} (epoch=2)
                                                    {CertificateVerify*} (epoch=2)
                            <--------               {Finished} (epoch=2)
{Certificate*} (epoch=2)
{CertificateVerify*}
{Finished}                  -------->
                            <--------               [ACK] (epoch=3)
[Application Data] (epoch=3) <------->              [Application Data] (epoch=3)

(Key notation: {} indicates encryption with Handshake keys; [] indicates encryption with Application Data keys)
```

### 2. Key Differences: DTLS 1.3 vs. TLS 1.3 vs. DTLS 1.2

- Record Layer Overhead Reduction: DTLS 1.3 introduces a variable-length unified header (DTLSCiphertext) that eliminates redundant version/type fields, compresses sequence numbers to 8 or 16 bits, and supports optional Connection IDs (CIDs).
- Sequence Number Encryption: Unlike DTLS 1.2, sequence numbers in encrypted records are XOR-masked using an sn_key derived via HKDF to prevent cross-path traffic correlation by on-path observers.
- ACK Message (Content Type 26): Replaces lock-step retransmissions with explicit ACK records for lost/reordered handshake messages and post-handshake flights.
- Cookie Exchange via HelloRetryRequest: Eliminates DTLS 1.2's standalone HelloVerifyRequest message in favor of TLS 1.3's standard HelloRetryRequest with a cookie extension to mitigate DoS/amplification attacks.
- Dedicated Epoch Tracking: Explicit epoch values map directly to key stages:
  - Epoch 0: Unencrypted (ClientHello, ServerHello, HelloRetryRequest)
  - Epoch 1: 0-RTT / Early Data
  - Epoch 2: Handshake traffic keys
  - Epoch 3+: Application traffic keys and rekeying generations

### 3. Summary of Major Features & Mechanisms

- Handling Datagram Unreliability: Solves loss, reordering, and fragmentation through per-message sequence numbers (message_seq), fragment offsets/lengths, ACK tracking, and retransmission state machines.
- Connection ID (CID) Support: Integrates RFC 9146 CID functionality natively to maintain associations across client IP/port changes (e.g., NAT rebinding, multihoming).
- AEAD Security Limits: Enforces hard usage caps on AEAD keys for both successful protections and unauthenticated/forged record attempts to defend against forgery and confidentiality degradation.
- Omission of EndOfEarlyData: Unlike TLS 1.3, the EndOfEarlyData message is omitted entirely due to epoch transitions making early-data boundaries explicit.
