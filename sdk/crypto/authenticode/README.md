## 1. Role

`sdk/crypto/authenticode/` implements the project's Authenticode verification path for Windows Portable Executable (PE) files. It extracts the embedded signature material, calculates the PE Authenticode image digest, compares it with the digest described by the signed content, and delegates signer/certificate verification to OpenSSL.

This module is a format-specific verification feature, **not a general-purpose PKI framework**. The current concrete format implementation is PE; the abstract plugin interface still carries hooks associated with separated signatures and other historical file formats.

## 2. Data Model

The verifier separates the file-format view, signed-content view, and certificate-validation state. These are related at runtime but are not interchangeable representations.

### File and signature representations

| Data | Meaning | Produced / consumed by |
|---|---|---|
| `file_stream` | Open target file; PE plugin may memory-map it to inspect headers and hash file regions. | `verify()`, `authenticode_plugin_pe` |
| PE DOS/NT headers and optional header | PE recognition and offsets/sizes for the security directory and checksum field. | PE plugin |
| Security-directory range | File offset and size of the certificate table; unlike ordinary PE data directories, the security-directory address is a file offset. | `read_authenticode()` |
| Authenticode payload (`binary_t`) | Bytes extracted from the certificate table and passed to OpenSSL as PKCS#7 content. | PE plugin → verifier |
| `PKCS7*` / SignedData | Parsed signature container, signer-info entries, and embedded certificates. | OpenSSL decoding / verifier context |
| `SpcIndirectDataContent` | Signed content containing the image-digest algorithm identifier and expected digest. | verifier |
| Calculated image digest (`binary_t`) | Digest generated by the selected file-format plugin using the Authenticode hashing layout. | PE plugin → verifier comparison |

The PE checksum and Authenticode image digest are distinct values. The checksum is a PE header field; the image digest is a cryptographic digest over the prescribed file regions with Authenticode-specific exclusions.

### Verification context and trust state

`authenticode_context_t` is an opaque context created by `open()` and released by `close()`. Its main state includes:

| Context data | Meaning |
|---|---|
| `engines` | Engine ID → plugin pointer; `load_engines()` registers the PE implementation for format selection. |
| `signer`, `trusted_cert` | Signer identifiers and caller-configured trusted certificate file/path entries. These are not the same as certificates embedded in the PKCS#7 container. |
| `flags`, `gender`, `pkcs7` | Verification mode and temporary/current signed-content state used by the implementation. |
| `crl_download`, timeout/retry, `crl_path` | Controls and location for optional CRL retrieval. |
| `proxy_url`, `proxy_user` | Optional settings passed to the external CRL download command. |
| `crl_map` | Context-level URI → `X509_CRL*` cache protected by `crl_lock`. |
| `lock`, `crl_lock` | Synchronization for engine/trust configuration and CRL cache state. |

During PKCS#7 verification, a second, local CRL map collects the CRLs available for that verification attempt and supplies them to the temporary OpenSSL `X509_STORE`. The context cache and per-verification map have different lifetimes: the former survives between calls until cleared with the context; the latter is used to assemble one store.

### Ownership boundaries

- The verifier owns the orchestration context and the registered engine references; callers use the opaque context through the verifier API.
- The PE plugin owns PE-format interpretation but writes extracted bytes and calculated digest to caller-provided output objects.
- OpenSSL objects (`PKCS7`, `X509_STORE`, `X509_STORE_CTX`, `BIO`, and CRLs) participate in decoding and verification. Their ownership varies by helper; the behavior section identifies where the store is assembled and where cached CRLs are retained.
- A trusted certificate path, a certificate embedded in PKCS#7, a CRL URI, a decoded CRL, and a successful trust/revocation decision are separate pieces of data. The presence of one does not imply the others.

## 3. Behavior Model

### 3.1 End-to-end verification flow

```text
caller
  │ open(&context), configure trust / CRL / proxy options
  ▼
authenticode_verifier::verify(context, filename, flags, result)
  │
  ├─ validate context and filename
  ├─ open file_stream
  ├─ select an engine by calling is_kind_of(file_stream)
  │    └─ PE plugin checks DOS header, e_lfanew, and NT signature
  │
  ├─ plugin.read_authenticode(file_stream, payload)
  │    └─ read security-directory range → certificate-table bytes
  ├─ OpenSSL decodes payload as PKCS#7 SignedData
  ├─ read SpcIndirectDataContent and its expected digest / algorithm
  ├─ plugin.digest(file_stream, algorithm, calculated_digest)
  ├─ compare expected and calculated digest
  │    ├─ mismatch / malformed input / missing engine → verification error
  │    └─ match
  │
  └─ verify_pkcs7(context, SignedData, ...)
       ├─ enumerate signer and embedded certificates
       ├─ resolve CRL distribution points and collect available CRLs
       ├─ create X509_STORE and load default/configured trust locations
       ├─ install verify_callback and CRL_CHECK / CRL_CHECK_ALL flags
       ├─ add decoded CRLs to the store
       └─ PKCS7_verify()
            └─ return status and verify_ok / verify_fail
  │
  ▼
caller receives return_t and result; close(context)
```

The digest comparison is a gate: PKCS#7 signer/trust verification follows only when the signed image digest matches the digest calculated by the selected engine. A successful digest comparison alone is not verification success. Likewise, `result` is a coarse `verify_ok` / `verify_fail` output; inspect the returned error code for the operation's failure category.

### 3.2 Engine selection and PE extraction

The verifier opens the target as a `file_stream`, then asks the registered engines whether they recognize it. The PE plugin ensures the stream is open and memory-mapped, checks that enough bytes exist for the DOS header, validates `MZ`, checks the NT-header offset against the stream size, and validates the `PE\0\0` signature. Recognition is not the same as complete structural validation: the later extraction and digest methods perform their own checks.

The PE plugin reads the optional header's security-directory entry to obtain the certificate-table file offset and size. The extracted certificate-table bytes are passed to OpenSSL for PKCS#7 decoding. The certificate table is not interpreted as an RVA-addressed data section; its address is a file offset. The plugin's `separated() == false` means the generic separated-file interface must not be interpreted as detached-signature support for PE.

### 3.3 Signed digest reconstruction and comparison

After PKCS#7 decoding, the verifier reads `SpcIndirectDataContent` to obtain the digest algorithm and expected image digest. It asks the PE plugin to calculate the digest over the file using the Authenticode layout. That layout treats the PE `CheckSum` field and certificate-table region specially; hashing every byte as a single opaque range would produce the wrong value.

If the calculated digest does not match the signed digest, the verifier returns a verification failure and does not proceed to signer-chain validation. If it matches, the verifier enters `verify_pkcs7()`. The PE `CheckSum` read/calculate/update APIs are a separate operation and do not replace this cryptographic comparison.

**Implementation detail:** `authenticode_verifier::verify()` calls the selected engine's `digest()` method without checking its returned `return_t`. Therefore, a digest-calculation error is not necessarily propagated as that original error code; the later digest comparison may determine the visible failure instead.

### 3.4 PKCS#7 trust and CRL preparation

`verify_pkcs7()` verifies that the decoded object is SignedData, enumerates signer certificates and certificates embedded in the container, and calls `get_crl()` for relevant certificates. When CRL downloading is enabled, `get_crl()` reads each certificate's CRL distribution-point URI, derives a local path, checks the context-level URI cache, and then tries the local file. If no local file is available, the current code can create the directory and invoke `wget` through the project's `process` abstraction using the configured retry, timeout, and proxy options. A downloaded/local file must still decode as `X509_CRL` before it is added to the maps.

The verifier then creates an `X509_STORE`, loads default trust paths and caller-configured trusted certificate files, installs `verify_callback`, sets `X509_V_FLAG_CRL_CHECK | X509_V_FLAG_CRL_CHECK_ALL`, and adds successfully decoded CRLs before calling `PKCS7_verify()`. Failure to retrieve or decode a needed CRL is not converted into a valid CRL; OpenSSL verification may fail. The implementation's exact callback behavior and signing-time exception are detailed in § 3.5.

### 3.5 Context lifetime, results, and failure boundaries

The caller opens a context, configures trust and options, calls `verify()`, and closes the context. The verifier's context contains engine registrations and CRL cache state, while temporary stream, PKCS#7 decoding, store, and verification objects belong to the current call. CRLs successfully retained in the context cache may be reused by later calls on that context.

Failure can occur at several distinct boundaries: invalid context/parameters, file-open or PE-layout failure, missing certificate-table payload, PKCS#7 decode or content-format failure, digest mismatch, CRL preparation, and PKCS#7 signature/trust verification. Do not collapse these into “bad signature”: the implementation reports return codes, while the separate output result provides the coarse verification status.

### 3.6 Current signing-time exception and CRL path

This subsection records the implementation visible in Revision 1107. It is a source-level behavior map, not a statement that the code implements every Authenticode or PKI validation requirement.

```text
authenticode_verifier::verify()
  │
  ├─ extract PE Authenticode payload
  ├─ decode PKCS#7 SignedData
  ├─ compare SpcIndirectDataContent digest with PE image digest
  │
  ▼
verify_pkcs7()
  │
  ├─ enumerate signer certificates and certificates embedded in PKCS#7
  │    └─ get_crl(cert)
  │         ├─ read CRL distribution-point URI(s) from certificate
  │         ├─ derive local cache/file path from each URI
  │         ├─ reuse context->crl_map entry if already cached
  │         ├─ otherwise read local CRL file
  │         └─ if absent, optionally invoke wget via process
  │              └─ decode downloaded file as X509_CRL
  │
  ├─ create X509_STORE and load default paths + configured trusted certificate files
  ├─ install verify_callback()
  ├─ set X509_V_FLAG_CRL_CHECK | X509_V_FLAG_CRL_CHECK_ALL
  ├─ add successfully decoded CRLs to X509_STORE
  │
  ▼
PKCS7_verify()
  │
  ├─ chain/certificate validation callback
  │    └─ if current error is CERT_HAS_EXPIRED and depth == 0:
  │         └─ is_valid_by_timestamp(current_cert, pkcs7)
  │              ├─ find PKCS#7 signer-info counterSignature attribute
  │              ├─ decode its inner SignerInfo
  │              ├─ read its signed signingTime attribute
  │              └─ compare signingTime with certificate notBefore/notAfter
  │                   ├─ within interval -> clear CERT_HAS_EXPIRED and accept callback
  │                   └─ absent/outside interval -> do not apply exception
  │
  └─ verification result -> success / verification_failure
```

#### What the current code does

1. **Timestamp extraction is narrow.** `extract_timestamp_time_from_signer_info()` looks for the PKCS#7 `counterSignature` attribute on a signer-info and reads the inner signer-info's signed `signingTime`. The current path does not establish, by this helper alone, that a trusted timestamp authority's certificate chain and timestamp-token signature have been validated.
2. **The exception only addresses signer-certificate expiry.** `verify_callback()` applies `is_valid_by_timestamp()` only for `X509_V_ERR_CERT_HAS_EXPIRED` at depth zero. It compares the extracted time against the current certificate's `notBefore` and `notAfter`. It does not apply this exception to every certificate in the chain or to every certificate-time error.
3. **The timestamp check is not a general historical validation mode.** The shown code does not configure OpenSSL to validate the entire chain at the timestamp. It handles the specific expired-signer-certificate callback case with a separate comparison.
4. **CRL retrieval and CRL policy are separate from the expiry exception.** `get_crl()` collects CRL distribution-point URIs and attempts local-file/cache lookup, with an optional external `wget` process when downloading is enabled. Successfully decoded CRLs are added to the store; `CRL_CHECK` and `CRL_CHECK_ALL` are set before `PKCS7_verify()`.
5. **Retrieval is not proof of successful revocation checking.** The sample enables downloading through `authenticode_ctrl_t::set_crl = 1`; it can be disabled for an air-gapped environment. If a needed CRL cannot be obtained or decoded, the code does not synthesize a valid CRL. The callback's `X509_V_ERR_UNABLE_TO_GET_CRL` case does not clear that error or force success, so the overall verification can still fail.
6. **The code path should not be described as “timestamp makes the certificate valid.”** It is more precise to say that a specific expired-certificate error at signer depth zero may be overridden when the extracted counter-signing time falls inside that certificate's validity interval. CRL checks remain separately enabled and can still affect the result.

#### Review points to revisit when the implementation changes

- Is the counter-signature `signingTime` the intended source of signing time, or should the implementation validate a standards-compliant Authenticode/RFC 3161 timestamp token and its TSA chain?
- Is the timestamp signature and its trust chain verified before its time is used as evidence?
- Should historical-time validation apply to the whole signer chain, and how should certificate validity and revocation status be evaluated at the relevant time?
- Are CRLs validated for issuer/signature, freshness (`thisUpdate`/`nextUpdate`), scope, and relevant certificate serial number as expected from OpenSSL's configured store checks?
- What is the intended behavior when a CRL URI is missing, unreachable, cached but stale, malformed, or yields no CRL? Should this fail closed, and how should the outcome be surfaced?
- Does the local cache need freshness/revalidation rules? The current context-level map reuses entries for the lifetime of the verifier context.
- Are tests needed for: expired signer with/without counter-signature time; time before `notBefore`, within the interval, and after `notAfter`; absent/unreachable/malformed/expired CRL; revoked versus non-revoked signer; and chain certificates at nonzero depth?

These are explicit review questions, not claims that each behavior is currently implemented or tested.

### Example from the source applet

`test/applet/authenticode/sample.cpp` demonstrates the concrete calling sequence: open a verifier context, set `authenticode_ctrl_t::set_crl` to `1` (with a source comment noting that it may be set to `0` for an air-gapped network), add `trust.crt` as trusted root material, call `verify()`, close the context, and report the result. It is an applet/sample rather than a dedicated `test/testcase/crypto/authenticode/` testcase directory.

A typical invocation shown in the source comments is `test-authenticate -v -i /path/to/target.exe`; the target file and `trust.crt` must be supplied in the environment. This documentation pass did not run the applet.

### Development Notes (for maintainer review)

- Source comments and revision history record the evolution from Windows SDK verification to OpenSSL and then to a plugin-oriented implementation. Keep this history distinct from the current supported-format claim.
- The plugin interface documents PE, MSI, and Cabinet as historical/intended engine types, but this directory's concrete implementation and this documentation scope are PE-focused.
- Although older source comments describe CRL retrieval as temporary or under construction, the current implementation includes an external-process download path and CRL-check flags. Treat this as an implemented mechanism, not proof of a complete production revocation policy. The sample currently enables CRL retrieval and comments that it can be disabled for an air-gapped network; actual outcomes still depend on certificate distribution-point data, network/process configuration, cache state, and trust-store settings.
