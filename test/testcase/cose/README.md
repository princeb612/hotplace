# COSE testcases

## 1. What

This directory contains testcases for COSE message processing and CBOR serialization. Its principal coverage areas are:

- RFC 8152 message structures and cryptographic processing, including signatures, encryption, MACs, recipients and COSE key import.
- COSE working-group examples supplied as YAML and CBOR data.
- Generated-key algorithm combinations, resource metadata checks, and RFC 8392 CWT examples.
- ML-DSA COSE operations and supplied JSON vectors when the OpenSSL version supports them.

The tests consume fixtures and exercise implementations in `sdk/crypto/cose/`; CBOR parsing and serialization are provided by `sdk/io/cbor/`. The `2. How` section describes the YAML field contract and how the consumer uses it; `3. Evidence` traces the actual field-consumption and verification paths.

## 2. How

### 2.1 Setup and dispatch

1. Build the `jose/cose` testcase target through the repository's existing CMake workflow. The COSE target's `CMakeLists.txt` copies `*.diag`, `*.cbor`, `*.yml`, and `*.json` fixtures into the runtime directory.
2. Run the executable from the expected working directory because fixture names are opened as relative paths.
3. The entry point configures logging and command-line options, calls `openssl_startup()`, then dispatches resource metadata, RFC 8152 examples, COSE YAML examples, generated-key COSE cases, RFC 8392 CWT cases and AKP/ML-DSA cases before cleanup and reporting.
4. Record the actual command line and OpenSSL/provider version with each report. The options below change coverage and should not be treated as cosmetic logging choices.

- `-b` skips the basic RFC 8152 `.cbor` fixture parse/publish round-trip; RFC 8152 cryptographic examples still run.
- `-g` skips the generated-key algorithm matrices in `testcase_cose()`.
- `-v` enables diagnostics and also enables explicit RFC 8152 fixture comparisons and YAML parse/compose byte comparison. It therefore changes the set of assertions executed.
- `-u` requests diagnostic CBOR publishing for generated messages; `-k` enables key dumps where consulted. These outputs are not correctness assertions.
- Debug/trace options are available only in `DEBUG` builds.

### 2.2 Procedure: RFC 8152 CBOR fixture round-trip

1. Unless `-b` is set, iterate over the paired RFC 8152 `.cbor` fixture files.
2. Memory-map each fixture and parse its original bytes with the CBOR reader.
3. Publish the parsed object back to CBOR bytes.
4. Compare the republished bytes with the original fixture bytes and release the parsed object.
5. Use this procedure to check deterministic parse/publish preservation. The human-readable diagnostic rendering is optional output, not the expected-value oracle.

### 2.3 Procedure: RFC 8152 message examples

1. The RFC example functions construct the message object tree directly: protected/unprotected headers, payload, signatures, recipient structures and algorithm identifiers are populated from the RFC example.
2. Publish the object tree to a CBOR byte sequence.
3. With `-v`, load the paired fixture and compare the generated bytes against it. The same branch parses and republishes the generated bytes and compares the resulting encodings; if the case enables untagged handling, it also removes the outer tag and compares the recomposed payload encoding.
4. Pass the generated bytes to COSE processing according to the top-level CBOR tag: Sign/Sign1 and MAC/MAC0 use verification paths; Encrypt/Encrypt0 use decryption paths.
5. Treat the operation's returned status as the result of this processing step. Do not infer payload equality or a true verification-result boolean unless a case has a separate explicit assertion.
6. Follow the RFC subcase's configured keys and headers: B exercises layered recipient information; C.1 exercises single, multiple and counter signatures plus criticality; C.2 covers ECDSA Sign1; C.3–C.4 cover ECDH/direct derivation, encrypted content, external data and Partial IV; C.5–C.6 cover MAC, derived keys and multiple recipients; C.7 covers public/private COSE_Key sets and key selection.

### 2.4 Procedure: COSE key import and selection

1. Read the public/private COSE_Key-set CBOR fixtures and parse them into CBOR objects.
2. Import the parsed key material through the COSE web-key adapter and build the RFC 8152 public/private key sets.
3. For compatibility checks, load the public and private key sets, then select keys by algorithm and key identifier.
4. Check the expected selected key and `kid` for the explicit ES512 and ES256 cases.
5. Sign with the selected private key and verify with the selected public key, checking the operation statuses. The test does not compare newly generated signature bytes to a fixed signature string.

### 2.5 Procedure: COSE working-group YAML examples

1. Load `testvector_cose_examples.yml` under the `COSE EXAMPLES` schema and build the key mapper from the example's key definitions. Key fields are decoded according to the declared base16, base64 or base64url encoding and grouped by `keyset`.
2. Iterate through each item. If its `skip` field is true, skip the item without processing it; otherwise decode its `cbor` hex string and select the referenced key set.
3. Parse the CBOR bytes and prepare diagnostic and binary representations. With `-v`, compose the parsed representation and compare the composed bytes with the parser's binary representation.
4. Open a COSE context and apply the optional shared parameters from the YAML item, including external AAD, IV, PartyU/PartyV identifiers, nonces and other shared/private information.
5. Call `cose.process()` with the mapped key set and CBOR message, close the context, and record the returned operation status.
6. Refer to the `COSE Examples YAML schema and field use` subsection above for the supported field layout. Do not treat a skipped item, printed output, or a successful status as an expected-plaintext comparison.

### 2.6 Procedure: generated-key algorithm matrices

1. Unless `-g` is set, generate the configured symmetric, RSA, EC, X25519 and Ed25519 keys. ML-DSA-44/65/87 keys are added only when the OpenSSL version meets the source's compile-time requirement.
2. For each configured signature algorithm, create a COSE signed message for the fixed input `hello world`, then process the generated message to exercise verification.
3. For each configured content-encryption algorithm and key-management algorithm pair, construct an Encrypt/recipient message, encrypt the fixed input, then process/decrypt the generated CBOR message.
4. For each configured MAC and key-management pair, construct a MAC message, generate it, then process/verify the resulting CBOR.
5. Record each sign/encrypt/MAC and follow-up process status separately. Unsupported algorithm combinations can fail; these loops are compatibility/operation exercises, not fixed known-answer tests. The code does not compare decrypted output with `hello world` or assert the verification-result boolean.

### 2.7 Procedure: COSE resource metadata

1. Iterate through the source's fixed table of COSE algorithm identifiers and expected key sizes.
2. Resolve each algorithm through `crypto_advisor::hintof_cose_algorithm()`.
3. Read the reported key size and compare it with the expected byte length.
4. Interpret a successful comparison as metadata consistency for the listed algorithms, not as proof that the provider can execute every algorithm.

### 2.8 Procedure: RFC 8392 CWT examples

1. Load the configured symmetric 128-bit/256-bit and EC P-256 COSE keys.
2. Process the embedded fixed CBOR examples for signed CWT (A.3), MACed CWT (A.4), encrypted CWT (A.5), nested CWT (A.6), and MACed CWT with a floating-point claim (A.7).
3. Dispatch to verify, decrypt or generic process according to the message type, and record the operation status for each example.
4. Treat the CBOR hex strings as fixed inputs; the testcase does not separately compare recovered claims or plaintext against decoded expected values.

### 2.9 Procedure: ML-DSA COSE and JSON vectors

1. On builds with OpenSSL 3.5 or later, create ML-DSA-44/65/87 keys, sign the fixed payload and process the generated COSE Sign1 message.
2. For each supplied AKP JSON vector, read the COSE key, Sign1 message, raw-to-be-signed field and raw public key.
3. Import the COSE key, extract its public-key bytes and compare them with the vector's raw public-key bytes.
4. Verify the supplied Sign1 message and record the operation status. The vector path does not regenerate the vector signature or assert the raw-to-be-signed field.
5. On older OpenSSL versions, the source records `not_supported`; that result does not establish successful ML-DSA execution.


### 2.10 COSE Examples YAML schema and field use

The YAML consumer in `testvector_cose_examples.cpp` loads the `COSE EXAMPLES` schema. The top-level `keys` list describes key records; `items` describes COSE message inputs and optional processing parameters. The variants below preserve the distinctions between EC, OKP, and RSA key records.

````yaml
testvector:
  - example: string             # [mandatory] testcase
    schema: COSE EXAMPLES       # [mandatory] "COSE EXAMPLES"
    keys:
      - item: string            # [mandatory] kid
        keyuse: string          # "enc"|"sig"
        keyalg: string
        keyset: string          # [mandatory]
        encoding: string        # [mandatory] "base64url"|"base64"|"base16"
        kty: ec                 # [mandatory] "ec"
        crv: string             # [mandatory] "P-256"|"P-384"|"P-521"|...
        x: encoding             # [mandatory] x
        y: encoding             # [mandatory] y
        d: encoding             # private material, where supplied
      - item: string            # [mandatory] kid
        keyuse: string          # "enc"|"sig"
        keyalg: string
        keyset: string          # [mandatory]
        encoding: string        # [mandatory] "base64url"|"base64"|"base16"
        kty: okp                # [mandatory] "okp"
        crv: string             # [mandatory] "Ed25519"|"Ed448"
        x: encoding             # [mandatory] x
        d: encoding             # private material, where supplied
      - item: string            # [mandatory] kid
        keyuse: string          # "enc"|"sig"
        keyalg: string
        keyset: string          # [mandatory]
        encoding: string        # [mandatory] "base64url"|"base64"|"base16"
        kty: rsa                # [mandatory] "rsa"
        n: encoding             # [mandatory] n
        e: encoding             # [mandatory] e
        d: encoding             # private material, where supplied
    items:
      - item: string            # [mandatory] filename/description
        keyset: string          # [mandatory] references a key set above
        cbor: hexstring         # [mandatory]
        shared:                 # optional shared processing parameters
          external: hexstring
          iv: hexstring
          apu_id: hexstring
          apu_nonce: hexstring
          apu_other: hexstring
          apv_id: hexstring
          apv_nonce: hexstring
          apv_other: hexstring
          pub_other: hexstring
          priv: hexstring
        enc:                    # optional encryption parameters
          aad: hexstring
          cek: hexstring
          tomac: hexstring
        skip: bit               # do not process this item
        untagged: bit
        debug: bit              # breakpoint/debug aid
````

The source consumer decides which fields are applicable to a particular message and key type. A field's presence in this schema does not mean it is used or asserted for every item; the case diagrams below distinguish decoded inputs, operation-status checks, and explicit comparisons.

### 2.11 How key records and message vectors are connected

Unlike most data-driven test suites in which each YAML row supplies input and expected output for a direct equality comparison, the COSE Examples vectors describe a small test environment in two linked parts: `keys` and `items`.

1. **Build the key set.** The consumer reads records under `keys`, decodes the key material according to each record's `encoding`, and uses the declared key type and parameters to create cryptographic key objects through the `cbor_web_key` path. EC, OKP, and RSA records carry different key fields, so the fields present depend on the key type.
2. **Associate a message with its keys.** Each `items` entry names a `keyset`. The consumer uses that name to find the corresponding key records; the message vector is therefore not self-contained and cannot be understood by reading its `cbor` field alone.
3. **Prepare and process the COSE operation.** The selected key material and the item's CBOR message are used together. Optional `shared` values (such as external data, IV, and party information) and optional operation parameters affect how the vector is processed. Flags such as `skip` can prevent an item from being processed.
4. **Interpret the result according to the actual assertion.** A successful COSE operation is not the same as an exact expected-output comparison. The evidence diagrams below identify which paths check operation status, compare bytes, or leave properties such as recovered plaintext without an explicit equality assertion.

This relationship is central to the fixture model: `keys` is test setup and key material; `items` is the operation-level test vector that refers to that setup by name. When adding or changing a vector, check both sides of the `keyset` reference and the consumer's handling of the selected key type.


## 3. Evidence

### Source-level coverage

The following diagrams trace the actual test branches and their explicit comparison/assertion points. The detailed procedures are in `2. How`; this section focuses on what the source proves and where the proof stops.

### Case 1 — RFC 8152 CBOR fixture round-trip

```text
for each RFC 8152 .cbor fixture
  → memory-map fixture bytes as expected
  → cbor_reader.parse(expected)
  → publish parsed object as CBOR bytes
  → assert published bytes == original fixture bytes
  → release parsed CBOR object
```

This path runs unless `-b` is supplied. It is a deterministic byte round-trip check for the parser/publisher representation. Diagnostic text is logged only when `-v` is enabled; the byte comparison itself is not verbose-gated in this helper.

### Case 2 — RFC 8152 source-built message versus example fixture

```text
RFC example function
  → build CBOR object tree (headers, payload, signatures/recipients)
  → cbor_publisher.publish(root) → generated bytes
  → if -v:
       load paired .cbor fixture
       assert generated bytes == fixture bytes
       parse generated bytes
       publish parsed bytes → assert == fixture
       publish parsed object → bytes → assert == fixture
       if untagging enabled and root is tagged:
         remove outer tag → recompose → compare payload bytes
  → dispatch generated bytes by root CBOR tag
       Sign / Sign1 → cose.verify(...)
       Encrypt / Encrypt0 → cose.decrypt(...)
       MAC / MAC0 → cose.verify(...)
  → assert operation return status
```

The exact fixture comparison, parse/publish comparisons, and optional untagged comparison in this helper are inside the `-v` branch. Without verbose mode, the source-built example still follows the cryptographic processing path, but those explicit fixture-byte assertions do not execute. Cryptographic verification/decryption is status-checked; the returned `result` boolean and decrypted plaintext are not independently compared with expected values in this helper.

### Case 3 — RFC 8152 B and C.1: layered recipients and signatures

```text
B — Two Layers of Recipient Information
  → construct nested recipient/message structure
  → serialize source-built CBOR
  → optional -v fixture/round-trip comparisons
  → process according to COSE tag → assert return status

C.1.1 — Single Signature
  → construct Sign1/Sign structure + key/signature parameters
  → serialize → optional -v fixture comparisons
  → verify using RFC public-key set → assert status

C.1.2 — Multiple Signers
  → construct multi-signer message
  → serialize → optional -v fixture comparisons
  → verify all message signatures through COSE processing → assert status

C.1.3 — Counter Signature
  → construct signed message with countersignature layer
  → serialize → optional -v fixture comparisons
  → verify/process message → assert status

C.1.4 — Signature with Criticality
  → construct critical-header example
  → serialize → optional -v fixture comparisons
  → verify/process message → assert status
```

These cases exercise distinct message structures, not five independent fixed-output checks in every run. Their cryptographic result is primarily represented by the COSE operation status; fixture byte equality is conditional on `-v`.

### Case 4 — RFC 8152 C.2: Sign1 / ECDSA

```text
C.2.1 — Single ECDSA Signature
  → build the RFC Sign1 example
  → serialize generated message
  → run do_test_cose_example(..., dountag=false)
  → unless -v: no explicit paired-fixture byte comparison
  → verify Sign1 using RFC public keys → assert return status
```

The helper is explicitly called with `dountag=false`, so this case does not enter the optional untagged-message recompose comparison. The signature operation is exercised, but the helper does not independently assert the verification-result boolean.

### Case 5 — RFC 8152 C.3–C.4: encryption, recipients, external data and partial IV

```text
C.3.1 Direct ECDH
  → build Encrypt / recipient structure → process with private-key set

C.3.2 Direct + key derivation
  → configure direct key derivation → process encrypted example

C.3.3 Counter Signature on Encrypted Content
  → construct encrypted content + countersignature → process

C.3.4 Encrypted Content with External Data
  → set external AAD inputs → process encrypted message

C.4.1 Simple Encrypted Message
  → load/add symmetric recipient key → process Encrypt0

C.4.2 Encrypted Message with Partial IV
  → construct Partial IV example → process Encrypt0
  → these C.4 calls disable untagged comparison

Each case:
  → serialize source-built CBOR
  → optional -v fixture/CBOR round-trip checks
  → cose.decrypt(...) → assert operation status
  → dump plaintext only on successful status and verbose logging
```

The examples cover different key-management and message-header conditions. A successful decrypt status is not the same as an explicit plaintext equality assertion; the helper does not compare recovered plaintext with a separate expected string.

### Case 6 — RFC 8152 C.5–C.6: MAC, key derivation and multiple recipients

```text
C.5.1 Shared Secret Direct MAC
  → construct MAC message → verify with configured key set

C.5.2 ECDH Direct MAC
  → configure ECDH-derived MAC key → verify

C.5.3 Wrapped MAC
  → configure recipient key wrapping → verify

C.5.4 Multi-Recipient MACed Message
  → construct multiple recipients → verify

C.6.1 MAC0 / shared-secret MAC
  → construct single-recipient-free MAC0 example → verify
  → dountag=false

Each case:
  → serialize source-built message
  → optional -v fixture/round-trip comparisons
  → cose.verify(...) → assert return status
```

These are operation-status checks. The helper passes a `result` output parameter but does not separately assert that boolean. The untagged recompose check is disabled for C.6.1.

### Case 7 — RFC 8152 C.7: COSE public/private key import and compatibility

```text
C.7.1 Public Keys / C.7.2 Private Keys
  → read .cbor COSE_Key-set fixtures
  → parse key objects and import through cbor_web_key
  → create rfc8152_pubkeys / rfc8152_privkeys
  → process associated example message(s)
  → optional -v byte/round-trip checks on example message

CWK compatibility:
  → load public and private key sets from COSE_Key CBOR
  → select keys by algorithm/key identifier
  → assert selected key and kid for ES512 / ES256
  → sign using private key → assert operation status
  → verify using public key → assert operation status
```

The explicit assertions here include selected-key identity metadata and operation statuses. The sign/verify helper does not compare a generated signature with a fixed expected signature byte string.

### Case 8 — COSE working-group YAML examples

```text
testvector_cose_examples.yml
  → parse schema "COSE EXAMPLES"
  → load keys by keyset (oct / EC / OKP / RSA)
       decode base16 / base64 / base64url material
  → for each item:
       if skip=true → continue without processing this item
       decode expected CBOR bytes
       parse CBOR → diagnostic representation / byte representation
       if -v:
         compose parsed CBOR → assert composed bytes == parsed bytes
       open COSE context
       apply shared parameters:
         external, IV, partyU/V ID/nonce/other, public/private other
       cose.process(keyset, CBOR, output)
       close context → assert operation return status
```

The YAML runner supports the six COSE tags (Encrypt0, MAC0, Sign1, Encrypt, MAC and Sign) and chooses the processing operation from the encoded message. A `skip` item is not a passing test. The runner does not compare every produced `output` with a YAML expected plaintext; verbose output, diagnostic notation, debug flags and decrypted bytes are observational. Its parse/compose byte equality is only asserted under `-v`.

### Case 9 — Generated-key sign, encrypt and MAC matrices

```text
test_keygen
  → create oct, RSA-2048, P-256, secp256k1, P-384, P-521,
    X25519 and Ed25519 keys
  → ML-DSA-44/65/87 keys when OpenSSL >= 3.5
  → assert key collection is non-empty

test_selfgen (unless -g)
  ├─ each signature algorithm:
  │    sign "hello world" → assert sign status
  │    process generated COSE message → assert status
  ├─ each content-encryption algorithm × each key-management algorithm:
  │    encrypt → assert status
  │    process/decrypt generated message → assert status
  └─ each MAC algorithm × each key-management algorithm:
       MAC → assert status
       process/verify generated message → assert status
```

The configured content-encryption matrix contains AES-GCM and AES-CCM variants; the signature list contains ECDSA, EdDSA, RSA-PSS, RSA PKCS#1 and ML-DSA where available; the MAC list contains HMAC and AES-MAC variants. The key-management list contains AES-KW, direct, HKDF, ECDH-based and RSA-OAEP variants. Unsupported combinations can return errors and are reported as such. The round trips do not compare decrypted plaintext to `hello world`, nor do they assert the verification-result boolean; they are broad operation-status exercises rather than fixed known-answer vectors.

### Case 10 — Resource metadata consistency

```text
fixed table of COSE algorithm identifiers and expected key sizes
  → crypto_advisor::hintof_cose_algorithm(alg)
  → read hint->enc.ksize
  → compare with expected byte length
  → assert equality for each table entry
```

This checks selected algorithm metadata and expected key-size values. It does not prove that each algorithm can be used successfully by every crypto provider.

### Case 11 — RFC 8392 CWT examples

```text
load symmetric 128/256-bit and EC P-256 COSE keys
  → RFC 8392 A.3 signed CWT → cose.verify → status check
  → RFC 8392 A.4 MACed CWT → cose.verify → status check
  → RFC 8392 A.5 encrypted CWT → cose.decrypt → status check
  → RFC 8392 A.6 nested CWT → cose.process → status check
  → RFC 8392 A.7 MACed CWT with floating-point claim → process → status check
```

The CWT messages are embedded fixed CBOR hex strings. The source records operation status for each message; it does not compare recovered claims/payloads to separately decoded expected values or assert the returned `result` boolean.

### Case 12 — ML-DSA COSE and JSON test vectors

```text
OpenSSL >= 3.5:
  create ML-DSA-44 / 65 / 87 keys
  → sign fixed payload → assert sign status
  → verify generated COSE Sign1 → assert operation status

For each AKP JSON vector:
  open JSON → read COSE key, Sign1, raw-to-be-signed, raw public key
  → load key into cbor_web_key
  → extract public key bytes → assert exact equality with raw_public_key
  → verify supplied Sign1 → assert operation status

OpenSSL < 3.5:
  → record not_supported
```

The vector consumer reads `raw_to_be_signed` but does not use it in an assertion. It does compare the imported key's public bytes with the fixed raw public key. Signature verification is status-checked; the returned verification boolean is not separately asserted. An OpenSSL-gated `not_supported` result is not a successful ML-DSA run.



### Cross-case interpretation

```text
Exact byte/value comparisons
  ├─ basic RFC .cbor fixture parse → publish → original-byte equality
  ├─ RFC 8152 generated-message / parse-publish comparisons → only with -v
  ├─ YAML parsed-message compose equality → only with -v
  ├─ resource table: reported key size == expected size
  └─ AKP: imported public-key bytes == raw_public_key

Operation-status checks
  ├─ RFC 8152 tagged message verify/decrypt/MAC
  ├─ COSE Examples YAML processing
  ├─ generated sign / encrypt / MAC matrices
  ├─ RFC 8392 CWT processing
  └─ ML-DSA sign / verify paths

Not independently asserted by the relevant helpers
  ├─ verification result boolean
  ├─ decrypted output == known expected plaintext
  ├─ YAML output == expected plaintext
  └─ generated signatures == fixed signature bytes
```

The `-v` option gates several explicit serialization comparisons, so it changes assertion coverage. `-b` and `-g` omit other test paths. Interpret a runtime report only with the actual command-line options and OpenSSL/provider version.
